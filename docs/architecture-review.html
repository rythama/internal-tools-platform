Architecture review · measured prototype

Renting the console, or owning it

Three internal tools today, ten more planned, $250K/year in platform licence. The question is not whether engineers can build a review queue — they obviously can. It is whether the eleventh one can get the audit trail wrong. We built it, then measured it. Both headline claims — that building is cheaper, and that guardrails make agent code safe — turned out to be false, and the second one is the more interesting failure.

What you are actually choosing between

Both systems put the same reviewer in front of the same case. The difference is not the screen — it is where the customer's tax ID comes to rest, who controls the record that says who looked at it, and what has to happen for the behaviour to change.

The invariant that makes it defensible

Owning the code only helps if the eleventh tool cannot quietly skip the controls the first one established. So the platform is built around a single structural property rather than a convention: there is no code path from the console to a domain table that does not write an audit row in the same transaction.

Not middleware, which can be forgotten. Not a logger, which can fail independently. One function, withAudit(), that commits the mutation and its audit record together or commits neither.

What the harness actually proved

The plan was that a verification harness written before the first session would make agent-authored changes safe to merge. So we tested that claim the only way it can be tested: by deleting each control and asking whether the suite noticed.

And the review that was supposed to catch it

Three pull requests, ~37 minutes of agent time, ~5,600 lines. Human review: 0 minutes, then 5–10, then 10–15. The first merged seventeen seconds after it opened, on a green check.

The model assumed review is the binding constraint and inflates on agent-authored code. That is not what happened. Review depth fell to fit the time available rather than hours rising to fit the code — the tax was not paid, it was skipped — and because CI stayed green, nothing signalled it. All three real defects were found by a rival agent session or an automated review pass. None by a human reading the diff.

What we are deliberately not replicating

Power Apps is not one product, it is three bundled capabilities. Only one of them is worth rebuilding, and being clear about the other two is the difference between a plan and a pitch.

CapabilityReplicate?Reasoning
Undifferentiated plumbing — auth, RBAC, tables, forms, audit, deploy yes Pure fixed cost. Paid once in packages/core, amortised across every tool. This is the entire opportunity.
Non-engineers building their own apps no Devin makes engineer-hours cheap; it does not turn an ops analyst into an app author. Different mechanism. Claiming otherwise oversells it, and the gap shows up as a ticket queue three months in.
1,000+ prebuilt connectors no Build the three or four integrations you actually use. Rebuilding a catalogue you don't need is how a platform project dies.
Vendor compliance posture partly A vendor's certifications never transfer to you — but they do shrink your evidence burden. Building moves that work in-house. Real cost, and it belongs in the model.
Escape hatch to arbitrary code only here The one capability a low-code platform structurally cannot offer. A tool that outgrows the spec drops into React against the same primitives instead of hitting a ceiling.

The recommendation, in one line: this is not a cost saving. Corrected for a baseline where Power Apps is first optimised in place, owning the stack never breaks even at any tool count, discount rate or horizon. Renting the UI layer reaches parity at roughly $125–145K/year and buys about 65% of the four primitives; owning the primitives underneath costs roughly $400K/year. The last 30% of compliance capability costs $260–275K/year — a legitimate purchase, and a fatal thing to mis-sell as savings.

Prototype built with Devin as the implementation tool; architecture, schema, core contract and CI authored by hand first, deliberately. SQLite stands in for Postgres so the repository runs with no infrastructure — a demo tradeoff, not a production recommendation. The recommendation's technical crux, binding a rented UI's queries to an identity it cannot forge, is untested here and is the proposed pilot's week-two gate.
